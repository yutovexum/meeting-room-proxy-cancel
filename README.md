# meeting-room-proxy-cancel

会議室予約システム：総務部管理者による代理キャンセル API（研修課題）

配布資料「会議室予約システム 要件定義書 v1.0」の F-4（総務部管理者による代理キャンセル）を実装したものです。F-1・F-2・F-3・F-5 は実装していません。

## 何を作ったか

| メソッド | パス | 内容 |
|---|---|---|
| POST | `/reservations/:id/cancel-by-admin` | 総務部管理者が、予約を代理キャンセルする |
| GET | `/cancellations` | キャンセル記録の一覧を返す |

### POST /reservations/:id/cancel-by-admin

本文（JSON）で `executorId`（実行者の社員ID）と `reason`（キャンセル理由）を送ります。

```json
{ "executorId": 3, "reason": "facility check" }
```

要件定義書 s9 の判定順序のとおり、上から順に判定し、最初に当てはまったものを返します。

| 順 | 条件 | ステータス | 本文 |
|---|---|---|---|
| 1 | 予約IDが指定されていない、または該当する予約が無い | 404 | 対象の予約が見つかりません。 |
| 2 | 実行者の role が ADMIN でない | 403 | 代理キャンセルの権限がありません。 |
| 3 | 理由が未入力（空文字・空白のみを含む） | 400 | 代理キャンセルの理由を入力してください。 |
| 4 | 理由が200文字を超えている | 400 | 理由は200文字以内で入力してください。 |
| 5 | 予約の status が BOOKED でない | 409 | この予約はキャンセルできる状態ではありません。 |
| 6 | 上記のいずれにも当てはまらない | 200 | キャンセルしました。 |

入力値は、要件定義書 s9「入力値の扱い」のとおりに扱います。

- 理由は、前後の空白を除去してから文字数を判定します。空白のみの入力は未入力として扱います。
- 予約ID・実行者IDは、数値として比較します。

検証に通った場合のみ、次の2つを行います。

- `reservations.status` を `CANCELED` に更新する
- `cancellations` に1行追加する（実行者・実行日時・代理区分・理由）

### GET /cancellations

200 と、キャンセル記録の一覧を JSON の配列で返します。

```json
[
  {
    "reservation_id": 1,
    "canceled_by": 3,
    "canceled_at": "2026-10-20T12:49:00.664Z",
    "is_proxy": true,
    "reason": "facility check"
  }
]
```

| 項目 | 列名 |
|---|---|
| 予約ID | reservation_id |
| 実行者 | canceled_by |
| 実行日時 | canceled_at（世界標準時。日本時間は9時間足す） |
| 代理区分 | is_proxy |
| 理由 | reason（前後の空白を除いたもの） |

### ログ

キャンセル操作のログは、`cancellations` への記録とします（要件定義書 s10）。コンソールには、起動時の `Server listening on port ...` の1行だけを出力します。

## どう動かすか

Node.js が必要です（v20.17.0 で確認しました）。

```bash
npm install
```

```bash
PORT=3000 npm start
```

PowerShell では、次のように2行に分けます。

```powershell
$env:PORT = "3000"
npm start
```

`PORT` を指定しない場合は 3000 で待ち受けます。データはメモリ上に持っているので、起動し直すと初期データに戻ります。

### 動作確認

サーバーを起動した直後に、別のターミナルで実行します。

```bash
node scripts/check.js 3000
```

判定1〜5、複数の条件に当てはまるときの判定順序、理由の200文字・201文字の境界、ID の数値比較、失敗したときにデータが変わらないこと、2回目のキャンセル、キャンセル記録の中身を、21件のケースで確かめます。本文の文言は、句点まで含めて完全に一致するかを見ています。2026年10月21日に実行し、21件すべて OK でした。21件の一覧と実行したときの出力は `docs/check-result.md`、セルフチェックリスト13項目の確認結果は `docs/self-check.md` にあります。

前のケースのキャンセル結果が次のケースに影響するので、実行するたびにサーバーを起動し直してください。

手で確かめる場合の例です（Windows の Git Bash から curl で日本語の理由を送ると文字化けするので、英語で送っています）。

```bash
curl -X POST -H "Content-Type: application/json" -d '{"executorId":3,"reason":"facility check"}' http://localhost:3000/reservations/1/cancel-by-admin
```

```bash
curl http://localhost:3000/cancellations
```

## 判断に迷った点

要件定義書に「書いていないことは足さない」「迷う箇所は実装せずに未決事項として報告する」とあるため、判定は追加せず、次のとおり扱いました。

### 未決事項として報告するもの

1. **退職済みの総務部管理者（id 4）が代理キャンセルできる**
   s9 の判定は「role が ADMIN でない」だけで、社員の status は見ていません。そのため、role が ADMIN で status が RETIRED の id 4 は、代理キャンセルに成功します（`node scripts/check.js 3000 retired` で、200 が返ることを確認しました）。退職済みの社員にも操作させない場合は、status の判定をどの順番に入れ、どの文言を返すかを決めていただく必要があります。
2. **管理者が自分の予約を代理キャンセルできる**
   F-4-1 は「他の社員の予約をキャンセルできる」と書いていますが、s9 には、予約者と実行者が同じ場合の判定がありません。今は、管理者が自分の予約を代理キャンセルすると、is_proxy が true で記録されます。
3. **要件定義書の環境と、課題の実行環境が違う**
   要件定義書 s10・s12 は Google Apps Script と Google スプレッドシートで構成するとしています。課題の指示（npm start で起動し、PORT で待ち受ける）に従い、JavaScript（Node.js と Express）で実装しました。

### 解釈して実装したもの

4. **実行者が存在しないとき、executorId が無いとき**
   s9 に専用の条件が無いため、「実行者の role が ADMIN でない」に含めて 403 を返します。
5. **理由が文字列でないとき（数値や null など）**
   未入力として扱い、400（代理キャンセルの理由を入力してください。）を返します。
6. **文字数の数え方**
   絵文字のように JavaScript の length で2と数えられる文字も、1文字として数えます。
7. **記録する理由**
   cancellations には、前後の空白を除いた後の理由を保存します。
8. **レスポンスの形式**
   課題文は「本文に文言を含める」とだけ書いていて、形式の指定がありません。そのため、文言をそのままテキストで返しています（JSON にはしていません）。GET /cancellations だけは、課題文の指定どおり JSON で返します。
9. **本文が JSON として読めないとき**
   Express が 400 を返します。要件定義書に定めが無いため、そのままにしています。
10. **コンソールへのログ**
   最初は動作確認のため、リクエストごとに判定結果をコンソールへ出力していました。要件定義書 s10 はキャンセル操作のログを cancellations への記録としていて、セルフチェックリストの13番目（書いていない機能を足していない）にも「ログ出力」が挙がっているため、提出前に削除しました。
